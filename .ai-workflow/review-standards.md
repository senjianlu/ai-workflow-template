# 评审标准(评审者手册)

本文件是本项目评审的唯一权威标准,由评审指令(.ai-workflow/prompts/review.md、
plan-review.md)显式引用。取舍与沿革见 docs/decisions/t0015。

评审者是本项目的独立评审者:只评审,不修改任何代码,也不在工作区新建或改动任何
文件(只读沙箱机器强制,任何写入都会失败);可执行的动作以下方「评审动作边界」
为准。

## 评审对象与核心问题

评审的阻断权只留给两类问题,其余意见一律不计入 pass/fail:

| 阶段 | 评审对象 | 核心问题(可阻断) |
|---|---|---|
| plan 评审 | 任务的 plan.md | 方案里有没有**设计错误**? |
| 实现评审 | 工作区的未提交改动(含新增文件),对照 plan.md 与本轮实现记录;评审对象以 review.sh 给出的本轮清单为准,不在清单中的未跟踪文件(被 `.gitignore` 忽略的,或项目登记在排除清单里的构建、运行期产物)不属于评审对象 | 改动里有没有**产品缺陷**? |

产品缺陷只有两类:

1. 产品代码在某个具体场景下行为错误——错误结果、数据损坏或丢失、安全问题、崩溃、
   未处理的失败路径、并发问题;
2. plan 承诺的行为未实现,或实现与 plan 不符且实现记录「与方案的偏差」表未声明。

评审者**不核验证据,也不评价测试是否充分**:证据由 evidence-check.sh 在评审启动前
机器判定(见「测试证据档位」);测试方面只回答一个不计入 pass/fail 的固定问题(见
「测试缺口」)。此外两级评审各有一个不计入 pass/fail 的固定问题——范围核对。

评审者**不给出 pass/fail 结论**。结论由脚本根据问题清单推导(见各阶段的「判定
规则」)。

## 评审动作边界

评审在**只读沙箱**中直审原仓库(机制见 docs/decisions/t0005),任何写入都会被沙箱
拒绝;评审动作以此为前提:

- **允许**:读取代码与 diff、grep 类检索、`git log` / `git blame`;运行**确无写入
  副作用**的只读检查(如 `tsc --noEmit`、禁用缓存的 lint)。命令因只读沙箱的写失败
  而报错时,**不视为代码缺陷**。
- **不运行任何测试**(含单元测试——多数 runner 需写缓存,只读下天然失败)。
- **超时与中止**:单条命令设超时上限(默认 5 分钟,建议用 timeout 等机制强制),
  超时即中止,不得反复重试拉长评审;疑似不自终止的命令一律不执行。
- **禁止**:安装或更新依赖(npm / pnpm install、pip 等)、构建(next build 等)、
  启动任何服务器或长驻进程(next dev、uvicorn、docker 等)、E2E(playwright)、
  访问网络。只读下多数天然失败,保留为行为约束:不得尝试。

**plan 评审的调查按需进行,不是例行步骤。**全量评审是第 1 轮的硬要求;调查只在
两种情况下才做——方案与评审者认为的最佳实践有出入,或方案存在明显的逻辑问题。
此时评审者先在仓库内只读调查、核实后再下结论:阅读相关的现有代码及其直接调用方、
数据模型、方案引用的 docs 与既有决策。没有上述疑点时,不为核对而通读代码库。

## 严重度定义(唯一权威来源)

- **plan-blocker**:方案/架构层面的错误,修改代码无法解决,必须退回方案阶段
- **blocker**:实现层错误,导致功能不可用、数据损坏或安全漏洞
- **major**:实现层缺陷,功能可用但存在正确性或健壮性问题,必须修复;其失败场景
  须在正常使用中可能出现(见「失败场景」),只在刻意构造的环境下才出现的至多 minor
- **minor**:产品代码的风格、可读性、边缘优化,可修可不修

**建议**不是严重度:不指向产品缺陷或设计错误的意见(测试、证据、任务记录、文档、
验收与用例表、措辞)都是建议,不计入 pass/fail,由开发 AI 处置(见「建议的标识与
处置」)。

## 实现评审

### 失败场景

每条 blocker / major 必须写明失败场景(输出的 `scenario` 字段):什么输入或状态 →
当前代码给出什么错误结果。写不出失败场景的意见不是产品缺陷。plan-blocker 的同一
字段写照此方案继续实现的后果。

**失败场景须在正常使用中可能出现。**blocker / major 的触发条件应当是真实用户、
真实数据或正常的运行环境会遇到的情形——攻击者能够控制的输入算在内,安全问题不因
"需要构造输入"而降级。只有在刻意构造的环境下才会出现的问题(例如文件名含控制
字符、毫秒级的改了又改回、有人手工改动工具自己的中间文件),至多列为 minor。拿不准
时问一句:这个项目的使用者在正常工作中会不会碰到它?

### 产品路径与非产品路径

每条问题带 `file`(问题首要位置的仓库相对路径;只有"plan 承诺的行为整体缺失、
没有对应文件"时才为空串)。review.sh 按它机器归类:

- 路径先做词法归一(去掉项目根前缀与尾部 `:行号`,折叠 `.`、`..` 与重复的 `/`);
- 命中"产品路径例外"清单 → 产品路径;否则命中"非产品路径"清单 → 非产品路径;
  其余(含空串、无法定位或越出仓库根的路径)→ 产品路径。

非产品路径缺省为:`.ai/`、`docs/`、根目录 `README.md` 与 `CHANGELOG.md`、测试目录
(`tests/`、`test/`、`__tests__/`、`e2e/`,任意层级)、测试文件(`test_*.py`、
`*_test.py`、`*.test.*`、`*.spec.*`、`conftest.py`)。目录按路径组件匹配,文件名
规则只匹配文件名本身,通配符不跨目录——`apps/test_management/api.py` 这样目录名
形似测试的产品源码不会被误归类。两份清单在 review.sh 内,标 `# TEMPLATE:`,按项目
增删(写法见清单上方的注释);产品路径例外缺省为空,用于文档即产品之类的项目。

### 判定规则

结论是评审输出与路径清单的纯函数,由 review.sh 推导:

1. **输入校验**:输出结构不合法(缺字段、字段类型错误、严重度取值非法)→ 评审
   无效,不发布评审文件。
2. **降级为建议**(带标记渲染,不丢失):
   - blocker、major、minor 位于非产品路径 →〔降级:非产品路径〕;
   - plan-blocker 的 `file` 只接受本任务的 plan.md、空串或产品路径,否则同样降级;
   - plan-blocker、blocker、major 的失败场景为空白 →〔降级:缺失败场景〕。
3. **结论**:余下有任一 blocker 或 major → **fail**,否则 **pass**。阻断问题不设条数
   上限,全部列出、全部计入。
4. plan-blocker 不计入 pass/fail,但置顶显著标注;minor 不计入。

### 分轮模式

review.sh 每轮保存所审改动的清单与内容快照,并在指令里注明本轮模式:

- **全量评审**(第 1 轮;以及第 2 轮起上一轮的评审文件、清单或内容快照缺失、
  HEAD 已变化,或两轮清单的纳入口径不同——项目的排除清单有变化,或上一轮清单由
  旧版脚本生成——的回退轮):审本轮清单中的全部改动。
- **修复核验**(第 2 轮起):脚本给出上一轮评审文件、变化文件列表与轮间差异文件
  (上一轮所审内容 → 本轮所审内容的 unified diff,即"本轮变化")。评审者:
  1. 先逐项核验上一轮的阻断问题,未解决的保留原严重度,summary 注明"上一轮 R-NN
     未解决";
  2. 本轮变化引入的问题按常规严重度列出,包括表现在未变化文件上的回归;为此可
     只读追查变化文件的直接调用方与依赖。标为"未快照"的变化文件(超过 1 MiB 或
     不可读)没有差异可看,整份按本轮变化对待;
  3. 与本轮变化无关的新发现:blocker 照列,其余至多 minor。

  变化文件列表里,存在性(新增、删除,含空文件)、文件类型(符号链接与普通文件
  互换)与可执行位的变化独立于内容差异列出。
- **所审内容一致性**:脚本在送审前与评审结束后各按同一口径重算一次清单,与本轮
  保存的清单不同(HEAD、文件内容、类型或可执行位有变,含 `.claude/` 下的 skill 与
  hook)→ 本轮评审无效,不发布、不消耗轮次。内容快照的副本也逐个核对哈希,与清单
  不符即视为快照生成失败。

### 测试缺口(不计入 pass/fail)

固定问题:本次改动里,哪些产品风险没有被任何测试覆盖?写入 `test_gaps`,至多
3 条,每条写明产品代码位置与未被覆盖的风险。只回答这个问题,不逐条评价测试用例
的断言强度。

## plan 阶段评审

plan-review.sh 在实现前审 plan.md,此时尚无实现,**不使用 blocker**。

### 可阻断的设计错误

plan-blocker 与 major 必须标明缺陷类别(`category`)并写明实现后果(`consequence`:
照此方案实现会导致什么)。类别标的是缺陷类型,与问题出现在 plan 的哪一节无关。

| category | 含义 | 可否阻断 |
|---|---|---|
| premise | 方案对现有代码、数据或环境的前提不成立;`detail` 须给出与方案矛盾的代码位置 | 可 |
| requirement | 方案缺失或做错了「需求原文」要求的东西,无法达成交付。单纯超出需求的追加不属此类,只进范围核对 | 可 |
| contract | 契约、数据模型、接口或失败路径设计错误 | 可 |
| convention | 与既有约定或现有行为冲突;plan 缺「需求原文」或「非目标」节(模板硬要求)也归此类 | 可 |
| feasibility | 方案自相矛盾或不可实施 | 可 |
| acceptance | 验收与用例表、证据档位方面的意见 | 否 |
| other | 措辞、不影响实现方式的表述不一致、docs 回写清单的遗漏 | 否 |

**返工判据**:若该问题留到实现阶段才被发现,是否需要推翻已完成的实现?是 → major
(或 plan-blocker);否 → minor。风格、个人偏好、等价写法之争一律不列。

### 判定规则

由 plan-review.sh 推导:输入校验同实现评审;plan-blocker 与 major 一视同仁——类别
不可阻断,或实现后果为空白 → 降为建议并带标记;余下有任一 plan-blocker 或 major →
**fail**,否则 **pass**。阻断问题不设条数上限。

同一 plan-blocker 严重度,在实现评审中不计入 pass/fail(单独升级人工),在 plan
评审中直接计入 fail——plan 阶段的全部目的就是拦截它。两套规则分域适用,互不覆盖。

### 分轮模式

默认最多 3 轮(用户明确要求时可经 plan.md frontmatter 的 `plan_review_max_rounds`
放宽,机制见 docs/decisions/t0003)。plan-review.sh 每轮快照 plan.md,并把模式、
上一轮评审文件与两轮快照间的修订 diff 注入评审指令。

- **全量评审**(第 1 轮;以及无上一轮快照的回退轮):逐一走完全部设计维度(达成
  需求、契约与正确性、前提、与既有约定的冲突、可实施性、范围自省),设计层问题
  **一次列全**,不得在找到前几条后停止;`overall` 逐维度各写一句检查结论。调查
  按需(见「评审动作边界」)。
- **核验评审**(第 2 轮起):① 逐项核验上一轮的阻断问题,未解决的保留原严重度;
  ② 修订部分(diff 中的改动)按上述维度完整评审;③ 未修订部分的新发现只有
  plan-blocker 可阻断,其余至多 minor。
- 评审期间 plan.md 被修改 → 本轮结论作废,不发布、不消耗轮次。

## 范围核对(不计入 pass/fail)

两级评审各有一个**固定问题**,结论写入输出的 `scope_findings`(字符串数组,每条含
定位与一句说明),渲染为评审文件的「范围核对」节;**不定严重度、不计入 pass/fail、
不重复列进 issues**,由用户裁决(机制见 docs/decisions/t0011):

- plan 阶段:方案是否超出「需求原文」?「改动范围」「实现方案」中不是需求直接
  要求的条目,plan 是否说明了"实现必需"的理由;顺手项是否已移入「非目标」。
- 实现阶段:diff 中是否存在 plan「改动范围」之外、且实现记录「与方案的偏差」表
  未声明的改动?偏差表中是否有标为「追加」但无用户确认记录的项?带〔机械性更正〕
  标注的用例,是否越出了笔误、排序、转义、算术的范围(改变用例意图、删减场景或
  放宽断言)?evidence-check 报告中的 EXTRA-ROW(plan 没有的用例)也纳入本项。

## 建议的标识与处置

评审文件里每条不计入 pass/fail 的条目都有可引用的编号:评审者自拟的建议 `A-NN`
(至多渲染 5 条)、测试缺口 `T-NN`(至多 3 条)、脚本降级的条目沿用原 `R-NN` 并带
降级标记。引用写作"阶段/轮次/编号",阶段取 `plan` 或 `impl`(如 `plan/01/A-02`、
`impl/02/R-03`)。`plan-review.sh __minors` 与 `review.sh __minors` 分别汇总两个阶段
全部轮次的 minor、测试缺口、建议与降级条目。

建议不触发修复轮,是否采纳由开发 AI 决定并留下一句理由(细则见 rawf-implement、
rawf-report);采纳建议不豁免追加类偏差规则。阻断问题上的分歧仍交用户裁决。

## 测试证据档位(开发侧契约,机器核验)

证据形态在 **plan 阶段**以契约形式定好:plan.md 的测试用例表逐条声明「档位」与
「证据形态」,实现者按契约留证,**evidence-check.sh 按契约机器核验**。评审者不核
证据。

机器负责判定的只有四件事,其余由实现者自证:

| 机器判定 | 实现者自证,不再有人核验 |
|---|---|
| 实现记录与 plan 用例表逐条对应、档位一致 | 被包住的命令是否真的验证了该用例 |
| 每条用例的结果是 `pass` | 用例是否充分 |
| A 档证据文件结构完整、属于该用例、退出码为 0 | B、C 档陈述的内容是否属实 |
| B、C 档的证据栏非空 | |

任一机器判定不满足,review.sh 不启动评审并开出补交清单,不消耗评审轮次。

### 档位

| 档 | 适用范围 | 证据形态 |
|---|---|---|
| **A** | 可由非交互命令判定的用例(单元测试、E2E runner、lint、tsc、grep/静态校验、脚本) | 由 `.ai-workflow/scripts/evidence.sh` 包住命令产出的 **rawf-evidence v1** 文件,落任务目录 `evidence/`;**exit 0 表示用例通过** |
| **B** | 靠静态事实即可确证的断言(配置生效、文案键存在、路由已注册) | 日志片段,或带 `文件:行号` 的代码/文档引用 |
| **C** | 确实无法自动化的人工交互验证(真机视觉、剪贴板、系统弹窗、跨设备) | 实现者陈述 + 关键锚点(相关代码位置、截图文件名、控制台片段) |

开发侧约定(plan 评审对它们的意见属于建议,不阻断):

- 凡可自动化者走 A 档,不降档;实现阶段不得下调 plan 已声明的档位。
- C 档条目数 ≤ 该 plan 测试用例总数的 1/3(向下取整;总数 < 3 时至多 1 条),每条
  写明为何不可自动化。
- 日志/文本证据优先于截图;截图不作为任一用例的唯一证据。

**A 档以 exit 0 表示用例通过。**被测命令预期以非零退出时,用断言包一层再留证
(如 `evidence.sh TC-07 -- bash -c '<命令>; test $? -eq 2'`),不得直接把非零退出码
当作通过。

### rawf-evidence v1 格式(A 档证据的唯一合法形态)

`evidence.sh <TC-id> [-l <label>] -- <命令...>` 写出
`evidence/<TC-id>[-<label>].log`,已存在则拒绝覆盖(重跑另起 label)。
文件结构与完整性定义(机制与取舍见 docs/decisions/t0010):

```
# rawf-evidence v1          ← 第 1 行,逐字
tc: TC-07                   ← 必填;须与引用它的记录行编号相同
label: r02                  ← 可空
cmd: pytest tests/test_x.py -v   ← 必填非空;argv 逐项 shell 引用,原样可复跑
cwd: /abs/path              ← 必填
git_head: <sha>[ dirty]     ← 必填
started: <ISO 8601>         ← 必填
--- output ---              ← 正文起始标记,独占一行
<stdout 与 stderr 合流,完整,不截断>
--- end ---                 ← 尾部起始标记;正文后先写一个换行再写本行
exit: 0                     ← 必填,0..255 整数;送审时须为 0
finished: <ISO 8601>        ← 必填
bytes: 1234                 ← 必填 = 正文区字节数
```

正文区 = `--- output ---` 行之后、**最后一个** `--- end ---` 行之前(不含其前导换行)
的全部字节,长度必须等于 `bytes:`;正文本身出现 `--- end ---` 字样不影响判定。

### evidence-check 的判定

plan 必须在 frontmatter 声明 `evidence_format: v1`。下列任一命中即不通过:

| 标记 | 含义 |
|---|---|
| NO-FORMAT | plan 未声明 `evidence_format: v1` |
| EMPTY-TABLE / MISSING-ROW / TIER-MISMATCH / DUP-ID / BAD-TIER | 用例表或结果表为空;记录缺少某条用例;档位与 plan 不一致;编号重复;plan 的档位不是 A、B、C |
| NOT-PASS / BLOCKED | 结果不是 `pass`;结果为 `blocked`(须先经用户裁决) |
| NO-REF / MISSING | A 档行未引用证据文件;引用的文件不存在 |
| NO-HEADER / BAD-HEADER / NO-BODY / NO-FOOTER / BAD-EXIT / TRUNCATED | A 档证据文件结构不完整 |
| TC-MISMATCH | A 档证据文件头的 `tc:` 与所在记录行的编号不同 |
| EXIT-NONZERO | A 档证据文件 `exit:` 不为 0 |
| NO-EVIDENCE | B、C 档行的证据栏为空 |

`EXTRA-ROW`(记录有、plan 无的用例)只列出、不影响结果,由评审纳入范围核对。

### 机械性更正

plan 测试表中意图明确的机械性错误(笔误、排序、转义、算术),实现者可按意图更正:
在原单元格内就地更正并追加标注
`〔机械性更正:原文「…」;理由:…;见实现记录 D-NN〕`,并在实现记录偏差表记"替代"。
以更正后的文字为准。改变用例意图、删减场景或放宽断言不属于机械性更正,须用户
裁决;评审在范围核对中指出越界的更正。
