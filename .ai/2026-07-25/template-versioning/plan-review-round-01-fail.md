# Plan 评审:第 01 轮

## 问题清单
- [plan-blocker] R-01 升级命令在模板生成的 consumer 仓库中没有可解析的上游 tag，核心增量升级机制无法执行。
  - 详情:定位：plan.md:16-18、79-85、98-111；现有 README.md:30 指定通过 GitHub “Use this template”创建项目。方案只写入 source URL 和 version，却没有配置/获取模板仓库的 tag 或 refs；consumer 的本地 Git 历史中通常不存在 v<旧>/v<新>，因此 `git diff v<旧>..v<新>` 会直接失败，且本地旧 CHANGELOG 也不会含新版本的升级指引。需在方案中定义无脚本的上游获取协议（包括模板 remote/ref 命名、防 tag 冲突、fetch 后使用的完整 diff refs，以及如何读取对应版本 CHANGELOG），并同时覆盖新项目和存量项目的基线认领流程；随后将该可执行链路纳入 README 验收。
- [major] R-02 TC-01 未真实验证受管路径归类的精确性，错误的升级覆盖边界仍可通过。
  - 详情:定位：plan.md:65-77、143、157-179。预期宣称固定的 6/5 项归类并逐类核验，但命令只检查指定文本是否作为子串出现，既不计数/比较精确集合，也不检查“整体替换”项是否同时落在人工合并行，或是否混入额外路径。比如额外把 `docs/` 列入整体替换、或将 `.claude/settings.json` 同时列入人工合并，均会通过，却可能在 consumer 升级时覆盖项目资产或产生错误合并策略。将 A 档命令改为解析两行后对两个精确、互斥的路径集合做等值比较，并对额外项与双重归类失败。

## 总评
证据契约本身合规：6 条用例逐条声明为 A 档并给出所需证据形态，且没有 C 档。方案的关键缺口是 consumer 无法取得用于 diff 的模板版本对象；在补齐该升级来源协议及其验收后再评审。
