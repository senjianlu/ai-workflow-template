## 背景与目标

1.5.0 引入了两处新行为,各留下一个已知的短板(均记在该任务的停车场):

- **评审快照**(review.sh 的 `review_paths`):所审改动 = 相对 HEAD 有差异的已跟踪
  文件 + 未被 `.gitignore` 忽略的未跟踪文件。工作区指纹用的项目排除清单
  `hash_excludes`(标 `# TEMPLATE:`,项目可增删)没有作用于它。项目里如果有未被
  `.gitignore` 忽略的构建产物目录,即使已经按 1.4.1 的指引加进 `hash_excludes`,
  每轮评审仍会被逐个算哈希、复制进任务目录,并出现在变化文件列表里。
- **plan 评审指令**(plan-review.sh 的 `build_round_context`):第 2 轮起把两轮 plan
  快照之间的修订 diff 全文内联进指令,而指令经单个命令行参数传给 codex(Linux 上
  单个参数约 128 KiB)。plan 很长且改动很大时,codex 会以 `Argument list too long`
  启动失败,原样重跑仍然失败。review.sh 在 1.5.0 已对同类内容限长,plan-review.sh
  没有。

目标:项目在一处(`hash_excludes`)登记的排除项,对指纹与快照同时生效;plan 评审的
指令长度有界,超长内容落盘供评审者按路径读取。

## 实现方案

### 1. 评审快照套用排除清单(review.sh)

**未跟踪文件的筛选。**两套规则各自独立判断,不合并进同一条命令:

- 规则甲(现有):`git ls-files --others --exclude-standard`——没有被 `.gitignore`
  等标准规则忽略;
- 规则乙(新增):`git ls-files --others` 加 `hash_excludes` 各项——没有被项目的
  排除清单排除,与工作区指纹列未跟踪文件用的是同一种调用。

进快照的未跟踪文件 = 通过规则甲,并且(位于 `.claude/` 下,或通过规则乙)。原有的
路径排除(`.ai/`、`.claude/settings.local.json`、`.claude/worktrees/`)不变。

分开判断的原因:git 里命令行模式的优先级高于标准忽略规则,合并后排除清单里的反选
模式(`!…`)会把 `.gitignore` 已忽略的文件重新带进快照。`.claude/` 下的路径只看
规则甲的原因:其下的 skill 与 hook 是评审对象,而排除清单里 `dist/` 这类不带锚点的
目录模式会命中 `.claude/skills/dist/` 之类的嵌套目录;指纹排除 `.claude/` 是因为
Claude Code 会在评审期间自动写 `settings.local.json`,与快照无关。

| 文件 | 改前 | 改后 |
|---|---|---|
| 未跟踪、被 `.gitignore` 忽略(无论排除清单怎么写) | 不进快照 | 不变 |
| 未跟踪、未被忽略、不在 `.claude/` 下、被 `hash_excludes` 排除 | 进快照 | **不进快照** |
| 未跟踪、未被忽略、位于 `.claude/` 下(`settings.local.json`、`worktrees/` 除外) | 进快照 | 不变 |
| 已跟踪且相对 HEAD 有改动(无论路径是否命中排除清单) | 进快照 | 不变 |

**纳入口径写进清单。**清单的 `head` 行增加第三列,存放口径摘要——`hash_excludes`
各项的哈希(只覆盖数组里写的参数本身;项目若用 `--exclude-from` 引用规则文件,
文件内容的变化不在摘要里,在脚本注释中注明)。第 2 轮起,上一轮清单的口径与本轮
不同(包括 1.5.0 写出的、没有这一列的清单)→ 回退为全量评审并注明原因,上一轮
评审文件仍附在上下文里。口径不同的两份清单若逐项比对,会把仍在磁盘上、只是这
一轮不再纳入的文件报成"删除"。口径相同时,轮间差异逐文件的生成规则不变。

摘要放在 `head` 行而不另起一行,是为了让 1.5.0 的脚本读到新清单时也能安全处理:
它把 `head` 行的内容整体当作 HEAD 与当前比对,对不上即回退全量评审;若另起一行,
旧脚本会把那一行当成文件记录。

快照与工作区指纹是两回事:本节只改快照的口径。指纹仍按 `hash_excludes` 原有的语义
计算(例如清单里用 `!audit.log` 反选的文件照旧计入指纹)。

**评审对象以清单为准。**每一轮的轮次上下文(含第 1 轮与回退的全量评审)都给出本轮
清单的路径,并说明:工作区里不在清单中的未跟踪文件——被 `.gitignore` 忽略的,或
项目登记在排除清单里的构建、运行期产物——不属于评审对象。实现评审指令的开头与
评审标准「评审对象」一栏各补同一句话。这样全量评审的取材范围、修复核验的变化
文件列表、送审前后的一致性比对,用的是同一份清单;被排除的文件同样不在工作区
指纹里。

### 2. plan 评审指令限长(plan-review.sh)

沿用 review.sh 的两个限值:单块内联上限 16384 字节,指令总长上限 100000 字节。

- **修订 diff**:不超过 16384 字节时照旧内联(代码栅栏包裹)。超过时写入任务目录的
  `.plan-review-raw-NN.diff`(命中既有的 `.plan-review-raw-*` 忽略规则),轮次上下文
  改为给出该文件的路径与字节数,并说明其中的改动即本轮的"修订部分"。评审者在只读
  沙箱里按路径读取。
- **落盘路径**只在需要落盘时才处理:同轮上一次留下的同名文件先清掉;清不掉(被
  目录占用、无权限)或写不进去 → exit 3,评审未启动、不消耗轮次。不需要落盘时,
  该路径被占用不影响评审。
- **总量兜底**:拼好的指令超过 100000 字节 → exit 3 并说明原因(指令模板被大幅
  改写等情形),评审未启动、不消耗轮次,而不是让 codex 以 `Argument list too long`
  启动失败。

评审期间 plan.md 不得修改的校验、轮次计数、分轮模式均不变。

## 风险与回滚

- **被排除的未跟踪文件对评审者不可见**:若项目把真正的源码目录误加进
  `hash_excludes`,其中新增的未跟踪文件既不进快照也不在变化列表里。这与它们现在
  已不在工作区指纹里是同一性质的问题,清单标有 `# TEMPLATE:`、由项目自己维护;
  已跟踪文件不受影响。
- **超长 diff 落盘后依赖评审者去读文件**:指令里写明了路径与"其中的改动即修订
  部分";评审者若不读,核验轮可能把修订部分当作未修订部分。实现评审的轮间差异在
  1.5.0 已是同样的做法。
- **进行中的任务升级后多一次全量评审**:1.5.0 写出的清单没有口径一行,升级后的
  下一轮会回退为全量评审(一次),之后恢复修复核验。
- **回滚**:`git revert` 本次提交即恢复 1.5.0 的行为;无数据迁移。
