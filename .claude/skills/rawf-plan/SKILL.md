# rawf-plan:方案阶段

## 步骤

1. 与用户对齐需求。有歧义先问,不要带着猜测写方案。
2. 创建任务目录 `.ai/<yyyy-mm-dd>/<task-slug>/`(日期用今天,slug 用简短
   kebab-case 英文);若同名目录已存在,询问用户是续做还是换名。同时在其下
   建两个固定子目录并各放 `.gitkeep` 占位(空目录才能随任务入库):
   `evidence/`(证据:测试输出、截图、验证记录)与 `assets/`(资源:Design
   稿、参考图、外部素材)。
3. 将任务目录相对路径(如 `.ai/2026-07-05/add-login`)写入 `.ai/.current-task`。
4. 调研代码库后,复制 `.ai-workflow/templates/plan.md` 到任务目录并填写,
   保持 `status: draft`,frontmatter 保留 `evidence_format: v1`(缺了它,
   evidence-check 会拒绝送审)。**「需求原文」与「非目标」为必填节**:需求原文
   引用用户原话并写一句话交付物;改动范围里不是需求直接要求、但实现必需的
   条目写明理由;纯顺手项移入非目标。plan 评审会就此做范围自省(结论进
   「范围核对」节,不计入 pass/fail)。
   **写作粒度**:plan 写到能判断方案对错、能验收为止——契约、数据模型、接口、
   验收标准、风险;不预写实现代码与逐行细节。plan 评审拦的是设计错误,方案对
   现有代码的描述要准确:以"前提不成立"为由的阻断是最贵的一类返工。
5. 测试用例章节为硬要求:每条含编号 TC-NN(不得重复)、前置条件、步骤、预期
   结果,且至少一条覆盖异常/边界路径。没有可执行的验收标准的方案不算方案。
   **证据契约同为硬要求**:每条用例须**逐条声明档位与证据形态**(档位
   权威定义见 .ai-workflow/review-standards.md「测试证据档位」)——
   - **可自动化者走 A 档、不降档**:凡能由非交互命令判定(测试、lint、tsc、
     grep、脚本)的用例都走 A 档;
   - **C 档 ≤ 用例总数 1/3 且须写明不可自动化的理由**(总数 < 3 时至多
     1 条);上限是上限不是下限,没有人工交互项时 C 档为 0 才是常态;
   - 证据形态优先取日志/文本;截图不作为任一用例的唯一证据;
   - **A 档以 exit 0 表示用例通过**:被测命令预期以非零退出时,证据形态写成
     用断言包一层(如 `bash -c '<命令>; test $? -eq 2'`)。
   证据由 evidence-check 机器核验,评审者不核;档位与用例表方面的评审意见
   属于建议,不阻断。测试写得够不够由你负责,不要指望评审兜底。
6. 【plan 评审闸,仅当本方案预计触及文件 > 10 时执行(≤ 10 不走此闸),
   在确认闸之前】
   以**后台方式**运行 `bash .ai-workflow/scripts/plan-review.sh`(Claude Code
   中用 `run_in_background`,`timeout` 不低于 4000000 ms),启动后
   **直接结束回合**、不轮询等待,完成通知唤回后再分流。退出码 3 = 执行异常:stderr 含
   "已终止"(看门狗)→ 重跑一次;其它把 stderr 报用户后停下。按结果分流:
   - fail(问题清单里有 plan-blocker 或 major,即设计错误)→ **就地修订
     plan.md**(尽量一次改完),重跑评审;脚本强制轮次上限(**默认 3 轮**),
     达上限(exit 3 提示"N 轮上限")仍不通过 → 停止,把分歧交用户敲定,
     不自行绕过。
   - 分轮模式(review-standards.md「分轮模式」):第 1 轮为全量评审,设计层
     问题会一次列全,尽量一次改完;第 2 轮起为核验评审,只核上一轮的阻断
     问题与修订部分。**修订纪律**:只改被指出的问题,不顺带扩写或重写未被
     指出的章节——每处新增文字都会成为下一轮的"修订部分"。
   - **建议不阻断**:评审文件「建议」节的条目(评审者自拟的 A-NN,以及脚本
     降级的条目)是否采纳由你决定,采纳的就地改 plan,不采纳的不必在 plan
     阶段处理——它们与未修的 minor 一起由实现阶段经 `__minors` 汇总交接。
   - **评审运行期间不得修改 plan.md**:脚本在评审结束后核对 plan.md 与本轮
     快照,不一致则本轮作废(exit 3,stderr 含"评审期间被修改",不消耗轮次),
     改完后重跑即可。
   - pass(问题清单里没有 plan-blocker 与 major)→ 继续。
   认为某条阻断问题是误报时,不"解释掉"后静默忽略,原样呈用户定夺。
   轮次上限仅当**用户明确要求放宽**时,才在 plan.md frontmatter 写
   `plan_review_max_rounds: <正整数>` 覆盖默认值,并在第 7 步摘要中声明;
   不得未经用户提出而自行写入或建议性写入该字段。
   评审模型同理:默认不指定,用 Codex 默认模型;仅当**用户明确点名** plan 评审
   的模型或推理强度时,才在 plan.md frontmatter 写 `plan_review_model: <模型名>`
   / `plan_review_effort: <强度>`(裸值,不加引号;两个字段互相独立),并在
   第 7 步摘要中声明,不得自行写入。要换模型在两轮之间改(评审运行期间不得
   修改 plan.md)。写法不对,或 Codex 不支持该取值(stderr 含"codex exec 执行
   失败")时脚本 exit 3、不消耗轮次,把 stderr 报用户。
7. 向用户呈现摘要:目标、改动范围、测试用例清单、主要风险;若跑过 plan 评审,
   附评审结论、所用轮次与「范围核对」节的条目(原样转述,交用户裁决)。
   摘要**必带「范围自省」**三问,各一行:① 需求原文要什么、交付是什么;
   ② 改动范围里哪些不是需求直接要求的、为何保留;③ 哪些顺手项已移入
   非目标。不量化,如实自判。明确请求确认。
8. 【确认闸】仅当用户明确表示同意后:将 plan.md 的 status 改为 approved,
   填写 approved_at(日期时间)。用户要求修改则改完回到第 7 步。
9. 在 status 变为 approved 之前,不进行任何源码改动(有 hook 强制)。
