# t0015:评审只拦产品缺陷与设计错误,结论由脚本推导,证据核验交给机器

- 日期:2026-11-24
- 背景:三个 consumer 项目(前端、API、爬虫)的评审记录统计——914 轮实现评审、
  1256 轮 plan 评审;问题指向按路径加关键词归类,属估算,统计脚本见
  `.ai/2026-11-24/review-product-gate/assets/analysis/`:
  - 实现评审的阻断问题(blocker/major)67% 指向测试、证据或任务记录,24% 指向
    产品源码;54% 的 fail 轮只因前者而 fail(2026 年 11 月为 59%,49/83);
  - 11 月的修复轮有一半(39/78)没有改动任何产品代码;
  - 11 月 plan 评审首轮通过率 12%,平均 2.8 轮;阻断问题 73% 关于验收与用例表,
    plan-blocker 只占 5/485。t0012 的"前两轮全量穷尽"上线后首轮通过率没有提高,
    11 月每个 fail 轮的阻断问题为 3.4 条,高于全量平均的 2.4 条;
  - 11 月 90 个任务共 416 次 Codex 评审,输入约 3.7 亿 token。

  成因在规则而非评审模型。评审标准把核心问题定为"用例是否真实覆盖并通过",
  评审者又不能运行测试(t0005),只能读测试代码推断其强度,这种意见没有上限;
  任一 major 即整轮 fail,测试层面的意见与产品缺陷有同样的否决权;plan 评审的
  "验收缺覆盖即 major"同样无界,且修订新增的文字成为下一轮的评审面;实现评审
  每轮都是全量重审,没有收敛机制;开发 AI 对任何评审意见都无权不修,只能照办
  或上报用户。用户明确接受推翻既有决策。
- 决定:
  1. **实现评审只拦产品缺陷,结论由脚本推导。**评审输出去掉自报的 `verdict`;
     每条问题带 `file`(首要位置)与 `scenario`(失败场景:什么输入或状态 → 当前
     代码给出什么错误结果)。review.sh 先校验输出结构(不合法即评审无效、不
     发布),再按 `file` 做路径归类:指向非产品路径(`.ai/`、`docs/`、根目录
     README / CHANGELOG、测试目录与测试文件;清单在脚本内,标 `# TEMPLATE:`,另有
     优先的"产品路径例外"清单)的 blocker / major / minor,以及失败场景为空白的
     plan-blocker / blocker / major,降为建议并带标记渲染;plan-blocker 的 `file`
     只接受本任务 plan.md、空串或产品路径。余下有 blocker 或 major → fail。
     阻断问题不设条数上限。
  2. **证据由机器核验,评审者不核。**机器只判四件事:记录与 plan 用例表逐条
     对应且档位一致;每条用例结果为 `pass`;A 档证据结构完整、归属本用例、退出码
     为 0;B / C 档证据栏非空。被包住的命令是否真的验证了用例、用例是否充分、
     B / C 档陈述是否属实,由开发 AI 自证。A 档统一以 exit 0 表示用例通过(预期
     非零退出的被测命令用断言包一层);evidence-check.sh 新增 `NO-FORMAT`、
     `DUP-ID`、`BAD-TIER`、`NOT-PASS`、`TC-MISMATCH`、`EXIT-NONZERO`、
     `NO-EVIDENCE` 七项判定,
     并取消"plan 未声明 `evidence_format: v1` 即跳过核验"的历史任务豁免。测试
     充分性只留一个不计入 pass/fail 的固定问题(测试缺口,至多 3 条)。
  3. **plan 评审只拦设计错误,默认最多 3 轮。**plan-blocker 与 major 须标明缺陷
     类别(`category`)并写明实现后果(`consequence`);可阻断的类别是 premise、
     requirement、contract、convention、feasibility,acceptance 与 other 不可阻断。
     类别标的是缺陷类型,与问题出现在 plan 的哪一节无关;单纯的范围扩张不属于
     requirement,只进范围核对(t0011)。plan-review.sh 把类别不可阻断或实现后果
     为空白的 plan-blocker / major 降为建议。第 1 轮全量评审(设计层问题一次
     列全),**调查按需**——只在方案与评审者认为的最佳实践有出入、或存在明显
     逻辑问题时才在仓库内只读调查;第 2 轮起核验评审(只核上一轮阻断问题与修订
     部分,未修订部分只有 plan-blocker 可阻断)。
  4. **修复轮只审修复。**review.sh 每轮保存所审改动的清单(类型、可执行位、内容
     哈希)与内容快照(单文件上限 1 MiB,只留最近两轮),第 2 轮起由脚本生成
     轮间差异文件(缺失的一侧按规则取 HEAD 版本或视为不存在),并在指令里给出
     变化文件列表;上一轮的评审文件、清单或快照缺失,或 HEAD 已变化时回退为
     全量评审。修复核验轮先核验上一轮阻断问题,本轮变化引入的问题(含表现在
     未变化文件上的回归)按常规严重度,与本轮变化无关的新发现只收 blocker、
     其余至多 minor。脚本在送审前与评审结束后各重算一次清单并与本轮保存的比对,
     快照副本也逐个核对哈希,任一不符即判评审无效——快照、轮间差异与发布的结论
     因此绑定在同一个工作区状态上(工作区指纹不含 `.claude/`,而其中的 skill 与
     hook 属于评审对象)。清单里的路径与符号链接目标统一做无歧义编码。指令经
     单个命令行参数传入,变化文件列表与证据报告各自限长内联,超出部分落盘。
  5. **建议由开发 AI 处置。**评审文件的「测试缺口」「建议」两节(含脚本降级的
     条目)不触发修复轮;是否采纳由开发 AI 决定并留一句理由,修复轮写入实现
     记录「评审建议处置」表,评审 pass 时写入 summary.md「评审建议及处置」节,
     收尾汇总给用户、用户可改判。每条都有可引用的编号(`A-NN`、`T-NN`、降级
     条目沿用 `R-NN`),引用写作"阶段/轮次/编号";`plan-review.sh __minors` 与
     新增的 `review.sh __minors` 汇总各阶段全部轮次的 minor 与建议——修复轮只审
     修复,首轮的 minor 不会在末轮重复出现,收尾不能只读最后一轮。采纳建议不
     豁免追加类偏差规则。阻断问题上的分歧仍交用户裁决。
  6. **失败场景须在正常使用中可能出现。**blocker / major 的触发条件应是真实用户、
     真实数据或正常运行环境会遇到的情形(攻击者可控的输入算在内);只有在刻意
     构造的环境下才会出现的问题至多 minor。这一条是本任务自身的实现评审暴露出来
     后追加的:四轮评审共 20 条阻断问题,全部指向产品脚本、无一指向测试——第 1 条
     决定达到了目的;但第 2 轮起的 11 条全部出在修复轮的快照与轮间差异代码上,
     场景一轮比一轮偏(文件名恰好等于另一个文件名的转义写法、毫秒级的改了又改回、
     有人在任务目录里建同名目录),评审者只要能构造出失败场景就判 major,靠加轮数
     收敛不了。用户裁定在本版补上这道门槛(该条与最后一次修复未再经评审)。
  - 沿用边界(t0011 不变):机械性更正是否越界,由"实现评审判 major"改为列入
    范围核对交用户裁决;plan 缺「需求原文」或「非目标」节仍判 major(类别取
    convention)。
  - 被否掉的备选:
    - **让评审者重新运行测试**——t0005 的资源事故理由仍成立,且读测试代码推断
      强度的问题不会因能跑测试而消失;
    - **只更换评审模型**——规则不变,任何模型都会照着"逐条核用例覆盖、任一
      major 即 fail"的要求去挑测试;
    - **保留 plan 评审 5 轮上限**——轮数不是浪费的来源,每轮从头再审才是;
      核验轮范围已收窄,3 轮足够;
    - **每轮阻断问题设条数上限**(初稿为 5 条)——通过路径与失败场景两道筛选的
      都是产品缺陷,按条数截断只会让第 6 条起的缺陷无处安放,并派生出"顺延到
      下一轮"的额外机制;用户裁定撤销;
    - **plan 评审第 1 轮例行调查**——每轮都通读相关代码的成本高;用户裁定按需。
- 影响:
  - 评审输出 schema 与评审文件格式不兼容 1.4.x:去掉 `verdict`,实现评审新增
    `file`、`line`、`scenario`、`test_gaps`、`advisories`,plan 评审新增 `category`、
    `consequence`、`advisories`;评审文件新增「测试缺口」「建议」两节。按 README
    版本规则本属 MAJOR,用户裁定按 1.5.0 发布,CHANGELOG 升级指引开头标注。
  - 取代关系:t0012 的分轮模式与默认 5 轮(返工判据、plan 快照、机械性更正、
    `__minors` 保留);t0010 的"评审对 A 档只核三件事"、两种留证写法与历史任务
    豁免(v1 文件格式、evidence.sh、结构核验保留);t0006 的评审逐档核验与档位
    违规判 major(档位划分保留为开发侧约定);t0003 的 plan 评审默认轮数(放宽
    机制保留);t0005 的"证据审查由评审者承担"(只读直审、不运行测试、完整性
    指纹保留)。
  - 涉及面:review-standards.md 重写,两份评审指令、两份 schema、review.sh、
    plan-review.sh、evidence-check.sh、三份模板、四个 rawf skill、CLAUDE.md、
    AGENTS.md、README.md 同步。
  - 已知取舍:上一轮内容快照里缺少清单登记的副本时(例如任务目录从备份恢复),
    脚本把该文件按"内容未保存"处理并继续修复核验,不回退为全量评审——只影响这
    一个文件的内容差异,其存在性与元数据变化照常列出。本任务第 4 轮评审对此有
    不同意见(impl/04/R-02),用户裁定维持现状。
  - 残留风险:
    - 测试质量不再有评审把关,机器只确认用例留了证且退出码为 0;靠开发侧
      自律、测试缺口提示与用户抽查。出现证据造假或测试空转的案例时,新增决策
      引入抽查。
    - 路径清单配错,或评审者把产品问题的 `file` 填成测试文件,真缺陷会被降为
      建议;降级条目带标记渲染,不丢失。
    - 评审者可能把测试意见写成 `file` 为空的产品问题,或标成可阻断的类别来
      规避降级;靠指令约束、失败场景与实现后果字段。出现系统性规避时再收紧。
    - 按需调查可能漏掉"读起来自洽、但对现有代码描述有误"的前提错误,留到
      实现阶段由开发 AI 读代码时发现。
    - consumer 升级时,在途任务里"预期非零退出"的旧证据与未声明证据格式的
      旧 plan 会被 evidence-check 拒绝;升级指引要求先收尾在途任务。
